# Design
1. `price_source.py`: Funktionen `search(query, max_price, country) -> list[match]`, `offers(match) -> list[offer]`, `history(match) -> dict` im bestehenden internen Format (siehe main.py: `fetch_idealo_live`, Felder product_name, offers[{merchant, price_eur, shipping_eur, total_eur, delivery, url, available}], price_history_90d/summary). `idealo.py` wird hinter dieses Interface gestellt; `apify.py` implementiert es.
2. Apify: `POST https://api.apify.com/v2/acts/<actor>/run-sync-get-dataset-items?token=…&timeout=60` mit Eingabe des Actors; Lauf-Kosten über `GET /v2/actor-runs/<id>` (`usageTotalUsd`) bzw. Header; Rotation round-robin über `APIFY_TOKENS`, bei 402/403/Limit nächstes Konto. Cache je Suchbegriff 30 min (vorhandener Preis-Cache).
3. Kosten: Tabelle `cost_events (id bigserial, at timestamptz, source text, kind text, usd numeric(12,6), units int, user_id uuid null, result_id text null, detail jsonb)`; Modellpreise je Modell als Tabelle im Code (USD pro 1 Mio. Input/Output-Tokens), überschreibbar per Env `MODEL_PRICES` (JSON). Tokens kommen aus der Modellantwort (`usage`); fehlt `usage` (LiteLLM nostream liefert teils null), Schätzung über Zeichen/4 und Kennzeichnung `estimated`.
4. Admin-API: `GET /admin/costs?days=30` → `{daily:[{day, source, usd, units}], by_user:[{user_id,email,usd}], apify_accounts:[{account, remaining_usd, used_usd}], totals}`; Restguthaben über `GET https://api.apify.com/v2/users/me/limits` je Token.
5. Admin-Web: Seite „Kosten“ mit Summen, Tagesbalken je Quelle, Tabelle je Nutzer, Apify-Konten mit Warnung.
